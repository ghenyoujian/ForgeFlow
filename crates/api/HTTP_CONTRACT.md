# ForgeFlow HTTP v1 implementation contract

Prefix `/api/v1`. DTO definitions: `crates/domain/src/{model,execution,commands}.rs`; planner semantic detail in `crates/planner/src/lib.rs`. Authentication: owner service bearer (`FORGEFLOW_OWNER_TOKEN`, minimum 24 bytes), per-Worker bearer from `FORGEFLOW_WORKER_CREDENTIALS_FILE` (legacy `FORGEFLOW_WORKER_TOKEN` when no file is configured), or password `POST /session {password}` returning `{data:{token,csrf_token,expires_in_seconds}}`. Cookie sessions require X-CSRF-Token on mutation. Same-origin requests only. Browser bearer sessions support logout. Password is Argon2id hashed in mode-0600 persistent auth.json.

Collections/detail: `{data:T, read_model_version,observed_at,source:"postgres",next_cursor}`. Commands: `{data:T,operation_id,replayed,request_id,source}`. Domain failures use canonical DomainError; Axum JSON extraction failures are framework rejections and need not have that envelope. Authority commands require `Idempotency-Key`; conflicting request reuses return 409. Update commands use expected_revision; append-only creates use their documented history/version guards. The read-only planning-scenario POST below is a query without command replay. Stable flow id `{project_id}:{flow_revision}`.

Implemented route families in api/src/lib.rs are authoritative. GET /projects and GET /projects/{id}; POST /projects full Project, PATCH project `{project,expected_revision}`. POST /projects/{id}/requirements full Requirement; GET same. GET/POST teams full Team. GET tasks; task detail `/projects/{project}/tasks/{task}`. GET flows; POST `/projects/{id}/flow-revisions` `{flow:FlowRevision,context?:CompileContext,expected_revision?:number,parent_guard?:FlowParentGuard}`. New flow revision omits expected_revision. GET `/flows/{project}:{revision}` or project scoped alias; GET `/flows/{id}/context`; POST `/flows/{id}/checks` `{}`; POST `/flows/{id}/commit` `{expected_revision}`. Only commit can grant COMMITTED; caller-supplied COMMITTED on draft save is rejected. Semantic digests recomputed server-side.

GET portfolio returns summaries `{project,task_count,active_attempts,succeeded_attempts,evidence_receipts,qualification}`. GET resources returns policy array. GET/POST project resources accepts `{policy,expected_revision}`. GET project attempts; GET attempt detail optional `?project_id`; server resolves globally otherwise. POST cancel `{project_id,expected_revision,reason}`. POST project admissions full AdmissionRequest; server overwrites actor+idempotency fields. GET/POST project evidence EvidenceReceipt (verification qualification is separate).

Generic project documents route `/projects/{p}/documents/{collection}` GET/POST `{id,expected_revision?:number,value:object}` for sources/contracts/contract_versions/schedules/milestones/findings/artifacts/flow_contexts/operations. GET/POST aliases sources,contracts,milestones,schedule. Generic contract write cannot grant frozen state. GET findings. Document revision injected by Store.

Worker routes match domain DTOs: POST workers/register WorkerRegisterRequest, workers/{id}/heartbeat WorkerHeartbeatRequest; workers/{id}/claim `{project_id}` -> `{envelope:ExecutionEnvelope|null}`. GET attempts/{id}/control `?project_id&generation&worker_id` -> `{valid,cancel_requested,lease_expires_at}`. POST worker-events WorkerEvent; execution-result WorkerResult, fenced durable submission. Process exit evidence never directly grants SUCCEEDED. GET artifacts/{id}/content optional project_id; descriptor `{path,sha256}` persists as artifact document, path confined to data_root/artifacts and digest verified. GET attempt logs offset/limit_bytes pages raw data_root/attempts/{id}/stdout.ndjson.

Worker POST `/attempts/{id}/native-controller` accepts strict `forgeflow.dsh-bridge.v2` RPC, frozen project/task/attempt/generation, and UUID `rpc_id` reused with identical bytes on retry. `X-ForgeFlow-Worker-Id` and scoped Worker authentication are mandatory. Operations are admit, model_request, model_settle, release, poll, cancel_ack and observe; the native plugin receives a private Worker UDS and no HTTP credential. Native RPC cannot certify parent process stop. Frozen native-child policy and model route govern all additional allocations and requests; absent policy denies children. Unknown model settlement retains capacity and cost remains UNKNOWN. Shutdown permits settlement/polling while refusing new admissions/model requests. Project snapshot exposes filtered native lifecycle/allocation/usage rows from the same read transaction.

Owner POST `/attempts/{id}/integration-recovery` accepts exactly `{project_id,intent_id,expected_intent_revision,reason}` with `Idempotency-Key`. Attempt and intent IDs must be UUIDs, the expected intent revision must be positive, and reason must contain nonblank text of at most 2000 bytes. The coordinated Store transaction checks the managed project, exact attempt/generation and existing irreversible commit decision, performs the intent revision CAS, increments only its revision, and records a protected `INTEGRATION_RECOVERY` operation with the original intent/request/actor. It does not change the original receipt, Git ref, attempt, lease or allocation. An existing accepted recovery for the intent requires replaying its original key; changed request reuse returns `409 IDEMPOTENCY_CONFLICT`, stale intent revision returns `409 REVISION_CONFLICT`, and worker credentials return `403 FORBIDDEN`.

The response is `202 {data,operation_id,replayed,source:"postgres"}`. Read settlement through existing GET `/operations/{operation_id}`. The recovery service calls the actual `IntegrationService.recover` on the registered managed repository and original frozen intent. It checks the durable verification snapshot and Git binding, continues the same ref CAS/finalization, and uses the existing pool adapter: ACTIVE pools retain atomic successor handoff, while ordinary release requires authorized DRAINING. No author, model request, candidate creation or oracle command is repeated. Success requires the actual FINALIZED intent, SUCCEEDED attempt and released original allocations; failures remain RECOVERY_REQUIRED with retained original evidence. Exact-key replay of an ACCEPTED operation can resume after API restart; settled replay returns the persisted result. If finalization committed before operation settlement, replay verifies the retained finalized snapshot and registers that actual result. New generic operations writes cannot create or overwrite this typed recovery kind. The original verify-and-integrate operation and its history remain unchanged.

Owner GET/POST `/projects/{p}/channel-pool` configures a `forgeflow.channel_pool.v1` controlled pool only from actual launched baseline attempts. Activation requires explicit UTC starts_at/ends_at, target_channels, worker_id, resource_profile_id, controlled_only:true, launch_grace_ms:2000 and exact distinct baseline_attempt_ids. Configuration is immutable. POST `/channel-pool/drain` and `/channel-pool/end` accept expected_revision and reason; drain requires explicit Owner authorization after the window and end requires settled scoped occupancy. Worker POST `/attempts/{id}/handoff-result` accepts the ordinary WorkerResult identity and durable event ID. Active-pool terminal acknowledgment and an eligible replacement admission commit together; missing replacement rolls back the whole acknowledgment. Elapsed time alone never permits ordinary release. Controlled pools provide no native DSH production qualification.

SSE GET projects/{id}/events?after=0; global alias `/events?project_id=...` requires project. Last-Event-ID `project:project_seq`; no global ordering asserted. Durable events polled in bounded batches, no transaction held for stream. GET system/info; unauthenticated GET /healthz validates DB.

Remaining integration/qualification: full registered execution-template assembly from user TaskSpec, actual profile configuration UI, typed decision/recovery/backup/export workflows, complete DTO OpenAPI generation, measured clean deployment/restore and all P0 runtime Gates. Source implementations below require real scope-matched runtime proof. Scope remains full P0; process exit and CRUD do not grant qualification.

Enterprise planning source contract (handlers `crates/api/src/planning.rs`, records `crates/domain/src/model.rs`, snapshot/history `crates/store/src/catalog.rs`, forecast `crates/scheduler/src/planning.rs`):

| Route | Body and successful response | Authority |
| --- | --- | --- |
| GET `/projects/{project}/planning-inputs` | No body; read envelope with the complete planning snapshot | Owner read; no pagination or lease |
| POST `/projects/{project}/task-estimates` | Full `TaskEstimate`; command envelope containing the persisted estimate | Owner append-only command; `Idempotency-Key` required |
| POST `/projects/{project}/planning-scenarios` | `PlanningScenarioRequest`; read envelope containing forecast and snapshot identity | Owner read-only calculation; no `Idempotency-Key` requirement or replay record |

All three reject worker service tokens. Same-origin checks apply. Cookie-authenticated POSTs require `X-CSRF-Token`, including scenario calculation; both POSTs are refused with `503 SERVER_DRAINING` during shutdown. Bearer owner sessions use the existing authentication contract.

GET planning-inputs returns `{data:{project,tasks,teams,documents,resource_policies,resource_limits,completed_task_ids,active_task_ids,revision,planning_input_digest,as_of,source:"POSTGRESQL_REPEATABLE_READ"},read_model_version:revision,observed_at,source:"postgres",next_cursor:null}`. `documents` contains `{collection,value}` for owners, task_estimates, schedules and queue_entries. Tasks omit REMOVED_FROM_PLAN; completed IDs require a SUCCEEDED attempt matching the current task_revision. Active IDs mean an attempt has no terminal_at, not verified live-process health. Resource-limit rows are `{scope_id,dimension,hard_limit,allocated}`. The project, task/team/document collections, policies, allocations and completion facts share one PostgreSQL `REPEATABLE READ READ ONLY` MVCC snapshot. `as_of` is sampled from the database clock inside that transaction; envelope `observed_at` is sampled later in the API.

`revision` is the project event cursor. `planning_input_digest` is a server-opaque semantic planning identity: clients echo it without recomputing it. Its material includes current task definitions excluding revision/fence_epoch, teams, owner/estimate/schedule documents, queue task ID/priority, resource policies and current-revision completed IDs. It excludes project DTO, event cursor, allocation counters, active IDs and observation times. A new event or allocation observation need not change the digest; a global policy change can change it without advancing this project's cursor. Each scenario consumes fresh authoritative counters even when the digest matches. This digest is not an execution approval or a frozen allocation reservation.

TaskEstimate body is `{project_id,estimate_id,task_id,task_revision,estimate_version,effort:{optimistic_hours,likely_hours,pessimistic_hours,rationale,source:"USER_REVIEWED_THREE_POINT"},duration_hours?:number|null,revision}`. Unknown fields are rejected. Effort values are finite hours in `[0,1000000]`, ordered optimistic ≤ likely ≤ pessimistic, with nonblank rationale. Optional duration is separate elapsed-duration hours in `(0,1000000]`; missing/null remains unknown and effort is never converted automatically. Body project_id must equal the path (`400 IDENTITY_MISMATCH`). The estimate must bind the current task_revision (`409 CONTEXT_STALE`, including a missing task). Each `(task_id,task_revision)` history starts at estimate_version 1 and advances exactly by one (`409 REVISION_CONFLICT` on stale/skipped versions). Use a new nonempty estimate_id each time; existing IDs cannot be overwritten. Required body revision is replaced by persisted document revision 1. The version/current-task checks and append are in the coordinated catalog transaction. Generic task_estimates document writes reject expected_revision, preserving append-only history. Actor-scoped catalog idempotency replay returns the original operation/value before new history validation; a different normalized command with the same key returns `409 IDEMPOTENCY_CONFLICT`.

Scenario body requires `{input_revision,start_at,end_at}` and accepts optional `{planning_input_digest?:string|null,availability?:[{start_at,end_at}],worker_scope_id?:string|null,task_ids?:string[],duration_overrides?:{[task_id]:hours}}`. Unknown fields are rejected. Omitted/null digest or Worker scope means absent; omitted arrays/maps default empty, while null arrays/maps are rejected. A supplied digest takes precedence over input_revision and must match the fresh snapshot; otherwise the legacy guard requires exact project event cursor equality. Guard failure is `409 REVISION_CONFLICT`. `end_at > start_at`; overrides are positive finite hours ≤1000000. Selected IDs are unique current task IDs; override keys must exist but need not be selected. Empty task_ids selects all unfinished tasks. Selection does not automatically include predecessors, so a missing unfinished predecessor stays blocked.

Availability is explicit RFC3339 time intervals normalized to UTC, positive and nonoverlapping, inside the outer request bounds. Omitted/empty availability uses one interval spanning start_at/end_at. The scheduler accepts at most 256 intervals, a first-to-last availability span of at most 366 days, and at most 10000 selected unfinished tasks. Jobs are nonpreemptive and must fit a whole interval. The outer request bounds alone are not limited to 366 days when narrower availability is provided. Duration precedence is USER_SCENARIO_OVERRIDE → latest TaskEstimate matching the current task_revision with duration → highest schedule baseline interval → UNKNOWN. A zero-length saved schedule interval or absent duration yields DURATION_UNKNOWN, never an invented date.

The deterministic `PRIORITIZED_NON_PREEMPTIVE_RESOURCE_LEVELING_V1` forecast observes all seven dimensions (active_slot, coding_slot, cpu_units, memory_bytes, build_permit, gpu_permit, provider_inflight), applicable global/project/team ancestor policies and the optional explicit Worker scope. Current allocations remain occupied for the entire window, including held/quarantined occupancy; no release time is inferred. Every policy must have all seven authoritative dimension rows. A task needs a positive active_slot request. Missing/paused lineage, Owner root or required policy layers produces RESOURCE_SCOPE_UNQUALIFIED. `worker_scope_id` identifies a policy with worker_id present; it does not verify current registration, live placement, executor binding or Worker qualification.

Scenario data is `{forecast:{algorithm,rows,blocked,dependency_lower_bound_hours,complete,assumptions},input_revision,requested_revision,planning_input_digest,input_changed_since_request,as_of,source:"POSTGRESQL_REPEATABLE_READ",worker_scope_id,execution_rights_granted:false,qualification:"PLANNING_PROJECTION_ONLY",worker_placement:"EXPLICIT_SCOPE"|"UNVERIFIED"}`. The read envelope has read_model_version:null because this data contains input_revision rather than revision. input_changed_since_request compares project cursors only; it may be true on a successful digest-guarded request. Rows include task/Owner/team IDs, planned_start/end, duration_hours/source, dependency critical-path/slack, resource_or_calendar_wait_hours and scope_ids. The dependency lower bound excludes resource/calendar waits and may be null. Blocking findings are MISSING_PREDECESSOR, DURATION_UNKNOWN, PREDECESSOR_UNSCHEDULED, RESOURCE_SCOPE_UNQUALIFIED and NO_FEASIBLE_WINDOW; they normally return 200 with complete:false. Invalid request selections/windows return `422 VALIDATION_ERROR`; malformed persisted inputs return `422 PLANNING_INPUT_INVALID`; graph cycles, duplicate dependencies and scheduler window/size errors return `422 PLANNING_INVALID`. Forecasts persist no dates, reserve no resources, grant no execution/completion rights and prove neither optimum dates nor OS/model capacity qualification.

Reviewed bulk assignment can use additive `parent_guard:{flow_revision,revision,source_revision}` on flow-revisions. `flow_revision` identifies the reviewed parent, `revision` guards its object revision, and `source_revision` guards the reviewed requirement source in the supplied CompileContext. The transaction requires a new DRAFT with matching parent_revision, a higher child flow_revision, no expected_revision for an existing child, and current authoritative context. Missing context is `400 CONTEXT_REQUIRED`; stale parent or incompatible proposal is `409 REVISION_CONFLICT`; stale source is `409 CONTEXT_STALE`; changing a retained task's Owner/team while an attempt has terminal_at null is `422 ACTIVE_ATTEMPT`. The proposal remains subject to Flow checks and the separate commit command; saving it grants no execution rights. Existing clients may omit parent_guard.

Machine-readable planning schemas are `contracts/task-estimate.schema.json` (body/record plus command receipt), `contracts/planning-inputs.schema.json` (GET response) and `contracts/planning-scenario.schema.json` (request plus response definitions). Schema validators register the referenced canonical files by their published $id URNs; OpenAPI embeds all referenced definitions. OpenAPI also documents the additive parent guard; unexpanded Flow/CompileContext fields still refer to canonical Rust DTOs. JSON Schema covers shape and individual limits; transaction state, cross-field ordering, dates, existence and revision guards remain server checks. `ops/update-http-contract.py` updates the source inventory while preserving the existing typed planning schemas and operation annotations. This source contract and JSON consistency checks do not qualify runtime concurrency, browser acceptance, large-project scheduling, or any product Gate.

Worker-only GET `/workers/{worker}/dispatch-events?project_id={p}&after={project_seq}` is a bounded committed-fact SSE stream for the registered Worker and its exact project. Events use `worker-dispatch` and `forgeflow.worker_dispatch.v1`; kinds are `TERMINAL`, `HANDOFF_WAKE` and `CURSOR`. Terminal/wake facts bind project, worker, attempt, lease, generation, task/revision, operation, base SHA and current state to PostgreSQL project sequence. Cursor facts contain only scope and sequence. SSE IDs are percent-encoded `project:worker:project_seq`; `Last-Event-ID` must match both scope components. Worker local process completion and the full immutable tuple must be confirmed and the terminal observation persisted before freeing a local slot; replacement work still uses ordinary authoritative claim and durable launch. This stream carries no model context and grants no scheduling or launch authority.


Milestone acceptance is an authority command: owner-only POST `/projects/{project}/milestones/{milestone}/accept` with `Idempotency-Key` and `{expected_revision,baseline_version}` (both positive integers, unknown fields rejected). It evaluates the current MANAGED project and exact milestone revision/baseline inside the coordinated catalog transaction. Client-supplied status, dates of acceptance, evidence, or PASS flags are never accepted.

For this implementation, `Milestone.required_work_packages` contains current `task_id` values (task/work-unit identities), and `required_gate_ids` contains their immutable `verification_plan_id` values. Both lists must be nonempty and distinct. These fields do not refer to the unused work_packages or gate_runs table rows. Every required task must have a matching current-revision successful attempt, independently verified candidate evidence, and a finalized integration receipt bound to the same attempt/generation/input and verification plan. Required requirements must exist and be covered by those tasks. The server records requirement revision/content digests, task revision/input/plan digests, and candidate/integration evidence identities; a prior arbitrary PASS document cannot grant acceptance. The finalized receipt proves verification against the main revision used for that integration; it does not assert the repository HEAD has remained unchanged since then.

Accepted records are append-only server facts in GET `/projects/{project}/documents/milestone_acceptances`, with document identity `milestone_id:baseline_version`, `project_id`, `milestone_id`, `baseline_version`, `milestone_revision`, `status:"ACCEPTED"`, `accepted_at`, `conditions`, and `evidence_refs`. Generic writes to this collection are rejected. Acceptance leaves the milestone baseline and due date intact. A changed plan baseline has no acceptance until separately evaluated; a stale prior acceptance is retained as history and cannot be overwritten to disguise changed task or requirement inputs. Normal actor-scoped command replay returns the original receipt as a replay, rather than a fresh evaluation. The calendar distinguishes unknown/query failure, pending acceptance, and an acceptance matching current milestone and task identities.

## Unsaved Flow draft checks

`POST /projects/{project}/flow-checks` requires Owner bearer/session identity and `Idempotency-Key`. The body uses the existing Flow write shape `{flow, context}` with a matching project and a supplied `CompileContext`. This is a read-only preview: requirements, Owner territories, input snapshots and contracts are refreshed from authority, task and Flow digests are prepared in memory exactly as at draft save, and the real compiler returns the existing `{data: CheckReport}` view. Findings include `rule_id`, `subject_ref`, `blocked_tasks`, `evidence_refs` and repair guidance, including actual cycle paths and missing predecessor IDs. No Flow, finding, event, operation, lease or idempotency record is persisted. A transport retry recomputes against current authority; this preview cannot approve a persisted revision. The existing `/flows/{flow}/checks` and commit routes retain their version-bound behavior. The endpoint accepts the same 32 MiB local request limit as Flow revision save.

Worker registration scope: `POST /workers/register` checks both `worker_id` and `project_id` against the authenticated Worker grant. A project-bound Worker must supply its project; omission/null or identity mismatch returns HTTP403 `WORKER_SCOPE_DENIED` before registration. Owner commands retain Owner authority.

For multiple Workers, set `FORGEFLOW_WORKER_CREDENTIALS_FILE` to an owned regular mode-0600 JSON file: `{ "schema_version": "forgeflow.worker-credentials.v1", "workers": [{ "worker_id": "...", "project_id": "...", "token": "..." }] }`. The file is opened without following symlinks and is bounded to 1 MiB. The list must be nonempty; Worker IDs and tokens must be unique; tokens require at least 24 bytes and must differ from the Owner and legacy Worker service tokens. Multiple Workers may share a project. Invalid configuration rejects startup without exposing credential values. With this file configured, only listed Worker tokens are accepted; the shared `FORGEFLOW_WORKER_TOKEN` has no authentication fallback. Credential rotation takes effect after a coordinated restart.

Caller identity binds registration, heartbeat, claim, control, execution bindings, results, handoff, native sidecar RPC, dispatch, artifact project scope and attempt reads. Gateway scope issuance additionally checks the stored attempt's assigned Worker and project. Caller-supplied path, header or body IDs cannot widen that grant. Without the credentials file, legacy service-token configuration remains supported, including optional `FORGEFLOW_WORKER_ID`/`FORGEFLOW_WORKER_PROJECT_ID` deployment bounds; this compatibility mode does not provide individual Worker credentials.

### Native model relay

`POST /api/v1/attempts/{attempt}/native-model?project_id={project}` accepts raw Anthropic streaming JSON from the assigned trusted Worker. Canonical generation/session/allocation/request/grant/body-digest headers bind an already admitted native model request; the server consumes it once before opening the exact configured model gateway connection. Replays, wrong models/caps, stale leases and identities are rejected; this path never issues a second model-budget permit. Provider credentials stay on the server. Native usage settlement waits for trusted upstream transport closure; missing or interrupted usage remains uncertain and quarantined. Strict Worker model relay requires a frozen preloader, dummy native credentials and network isolation; legacy direct-observed profiles retain their explicit unqualified egress scope.

Event retention uses a logical database archive while keeping full paginated history. `FORGEFLOW_EVENT_RETENTION_SECONDS` defaults to2592000 and `FORGEFLOW_EVENT_ARCHIVE_INTERVAL_SECONDS` to3600; both accept1..315360000, with1000 archived events per bounded pass. Initial SSE requests outside the retained window return409 `SNAPSHOT_REQUIRED`. A live subscription that loses a contiguous replay window emits `stream_error` with that code and terminates; fetch a current snapshot and resume at its project cursor. Historical payloads and project event sequences are preserved.
