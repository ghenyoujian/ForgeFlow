# ForgeFlow

**面向多人与多 Agent 协作开发的控制平台。** ForgeFlow 探索把人员、Agent、项目需求、任务流程、资源和交付证据连接起来，使团队能够规划工作、监督执行并审查结果。项目采用 Rust、PostgreSQL 和 React，目标是支持企业场景下可追溯、可恢复、可扩展的协作；当前仍处于开发与验证阶段，尚不能据此认定已具备企业生产资格。

> 本项目按非商业许可提供源代码，禁止未获授权的商业使用；商业使用须另行取得权利人的授权。非商业限制与开源定义对使用领域不设限制的要求不同；具体权利和限制以 [LICENSE](LICENSE) 为准。

## 为什么构建 ForgeFlow

在多人和多个 Agent 同时开发时，任务依赖、修改权限、模型调用、资源占用、集成顺序与结果验收很容易分散到不同工具中。ForgeFlow 的方向是在同一控制面中表达这些关系，将任务计划与实际执行事实分开，并让代码、验证结果与交付证据可以关联审阅。它不是以 Agent 回复成功、进程退出码为零或界面显示完成作为业务验收依据。

## 能力与设计方向

- **项目与任务协作**：围绕项目、需求、团队、任务和 Flow 管理协作，明确工作分工、依赖与验证计划。
- **执行与资源管理**：由控制服务和独立 Worker 协作，接入受管执行器；记录尝试、租约、资源和生命周期信息。DSH 集成需要单独部署、配置并校验，不能由控制台启动替代。
- **代码与证据**：面向 Git 的源码管理、候选结果、串行集成和证据关联，支持对交付物与验证过程进行审阅。
- **运行与恢复**：以 PostgreSQL 和数据目录保存状态，提供事件、备份和恢复相关机制；运行故障与恢复结论需要按实际场景分别验证。
- **管理界面与 API**：通过 React 控制台及 Rust API 查看和操作项目、任务、执行和证据。具体可用功能与部署配置以实际版本和验证记录为准。

这些描述概括仓库现有实现和设计方向，**不代表每条端到端链路、每种异常场景和目标规模已经验收**。相关设计和未完成事项见 [ECP 文档](docs/ecp/)。

## 总体架构

```text
 人员 / 协作界面                  外部 Agent / 执行器
        │                                ▲
   React 控制台                           │
        │ HTTP / SSE                     │
        ▼                                │
 Rust 控制服务 ── 规划 / 调度 / Git / 证据 ── Worker
        │                                │
        ▼                                ▼
   PostgreSQL / 数据根                 受管执行环境
```

控制服务维护项目与执行事实，Worker 负责受监管的执行。执行器、模型配置、沙箱、凭据和真实工作负载需要由部署者单独提供并验证。历史设计、原型和有限实验不得自动视为当前版本的生产资格。

## 开始使用

### 环境要求

源码开发面向 Linux 或 WSL2：需要 Git、Rust 工具链（项目使用 Rust 2024 edition；容器构建使用 Rust 1.90）、Node.js 22 和 npm。原生服务需要 PostgreSQL 16；容器示例需要 Docker、Compose 和可用的镜像及依赖下载网络。运行真实 Agent 工作负载还需要与部署配置匹配的 DSH、模型、执行器和隔离环境。请使用独立测试数据库、数据目录和凭据，阅读部署文档后再接入项目。

### 构建源码

以下命令会下载依赖并构建软件；执行前请检查本机资源及依赖来源：

```bash
cargo build --locked --workspace --bins
cd console
npm ci
npm run build
```

仅构建不启动服务，也不证明任务执行和交付有效。安装路径、迁移、密钥、Worker 与运行配置见[部署手册](deploy/RUNBOOK.md)。原生安装流程需要已生成并核验的构建收据与前端产物，并非刚克隆即可直接安装的预构建发行包。

### 本地容器体验

仓库包含 Lite Compose 配置，仅提供控制服务和 PostgreSQL，**不包含 Worker、DSH 或模型服务**。先复制 `deploy/env.example` 到仓库外的私有文件，设置数据库密码、至少 12 字符的负责人密码，以及两个不同的随机 Owner/Worker 令牌（至少 24 字符），并限制该文件权限。不要提交私有配置或密钥。然后从仓库根目录运行：

```bash
docker compose --env-file /path/to/private/forgeflow.env \
  -p forgeflow-lite -f deploy/compose.lite.yml up --build -d
docker compose --env-file /path/to/private/forgeflow.env \
  -p forgeflow-lite -f deploy/compose.lite.yml ps
curl --fail http://127.0.0.1:8787/healthz
```

默认访问 `http://127.0.0.1:8787`，使用配置的负责人密码登录；端口可通过 `FORGEFLOW_HTTP_PORT` 调整。停止服务使用同一参数执行 `docker compose ... down`，默认保留数据卷。容器路径在历史记录中尚未获得干净系统的构建及启动资格，以上为源码提供的体验入口，并非经过当前发布版本复测的生产安装承诺；健康检查也不证明 Agent 协作闭环通过。

真实 Worker 和 DSH 的准备、凭据及执行器 Doctor 参见 [Worker 文档](crates/worker/README.md)和[本地部署指南](deploy/QUICKSTART.zh-CN.md)。首次运行应从小规模、独立环境开始，避免使用真实生产数据作为试验材料。

## 验证与路线

后续工作以多人和多 Agent 协作主线为准：先明确权限、状态与资源边界及数学/形式化假设，开展低成本反例和模型验证；再推进真实端到端协作、故障恢复与安全边界，最后以受控负载评估稳定性、性能和扩展性。每一阶段应记录解决的问题、证据、未解决问题及对主线的影响，并保留失败结果。

验收需要对应版本的理论与设计依据、对照或消融、边界与异常测试、真实端到端工作负载、性能结果及可复现证据；单纯通过构建、单元测试或健康检查不足以证明有效性。受控轻量通道与真实 DSH 会话是不同工作负载，已有的局部或历史实验不能代替真实多 Agent 并发和企业部署验证。当前不宣称所有 Gate 已通过，也不将目标规模作为已实现容量。部分既有受控资格脚本依赖未公开的历史运行证据、外部环境或固定产物，不能仅凭此公开仓库直接复现原有结论；重新验证需要建立独立环境并生成新的证据。
