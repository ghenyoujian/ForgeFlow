# Local deployment and operations

For persistent local operation, use `python3 ops/manage-service.py install --release-dir /absolute/forgeflow-version --runtime-env /absolute/private/runtime-env.json --start`. A user systemd manager must be running. Stop an existing foreground server first. The service loads owned mode-0600 private JSON, checks the installed binary against its delivery manifest, and restarts failed processes. Credentials stay out of the unit. Inspect with `systemctl --user status forgeflow-control.service`; stop with `systemctl --user stop forgeflow-control.service`. Enablement starts it with the user manager; continued operation after logout depends on the system's user service policy, and this does not keep a stopped WSL instance alive. Use a separate `--name forgeflow-worker-main --worker-config /absolute/private/worker.json` unit for an explicitly configured Worker. Version changes require draining attempts, stopping the unit and reviewing its new release path; differing existing units are not overwritten automatically.

Use a Linux filesystem for installation and persistent data. Install into a fresh explicitly selected `FORGEFLOW_INSTALL_ROOT`; installation refuses an existing directory or symlink and never starts services. The installer reuses existing binaries and console assets without running Cargo/npm. It includes `forgeflow-server`, `forgeflow-worker`, `forgeflow-sandbox-guard` and `forgeflow`.

For an existing successful immutable build checkpoint and built console:

```bash
FORGEFLOW_INSTALL_ROOT=/absolute/fresh/forgeflow-version \
  ops/install-local.sh --checkpoint /absolute/checkpoint/receipt.json \
  --console-dist /absolute/control/console/dist
```

To prepare a transferable local directory package and install it independently:

```bash
python3 ops/package-checkpoint.py create \
  --receipt /absolute/checkpoint/receipt.json \
  --console-dist /absolute/control/console/dist \
  --output /absolute/fresh/forgeflow-package
python3 ops/package-checkpoint.py verify --package /absolute/forgeflow-package
FORGEFLOW_INSTALL_ROOT=/absolute/fresh/forgeflow-version \
  /absolute/forgeflow-package/ops/install-local.sh --package /absolute/forgeflow-package
```

For complete source delivery, add `--source-archive`, its explicit `--source-archive-sha256`, the actual `--source-prefix`, and the selected `--evidence-index`/`--evidence-index-sha256`. The original fixed parent Python archive and design Markdown are also copied to `source-support/`; explicit `--legacy-archive`/`--design-plan` paths each require their SHA256. See [delivery contents and exact commands](DELIVERY_CONTENTS.md) and [Chinese quick start](QUICKSTART.zh-CN.md). Verify it with `--require-complete-source`. Migrations, API/Schema, architecture, user guide, task matrix and known risks are copied alongside the runtime; a supplied source archive must match the original Rust compilation inputs, frontend source and all copied delivery resources. Selected original evidence is copied with its declared status and scope.

`delivery-manifest.json` pins every packaged file, permissions, all four original binary SHA-256 values, the unchanged original build receipt and available logs, and the immutable DSH preset source. It preserves the actual build scope. A debug checkpoint produces a package labelled `debug` and `ENGINEERING_CHECKPOINT_ONLY`; packaging adds no production, frontend build, DSH or concurrency qualification. An actual successful Cargo build and matching build log are required. Failed checks are preserved as recorded; missing or overwritten test logs are listed explicitly in `build.unavailable_test_logs`, and `build.verification_status` becomes `INCOMPLETE`. The script does not fabricate replacement logs or convert that candidate into a qualified release. The existing `console/dist` bytes receive independent file hashes because the Rust receipt excludes frontend compilation. The directory package contains no database, runtime configuration, private model credentials or live state. It requires compatible Linux dynamic libraries, PostgreSQL and separately configured DSH/sandbox tools; Compose requires the complete source checkout for its image build. An interrupted operation leaves `.INCOMPLETE`; use another fresh directory. To build new binaries or console assets, use the source checkout's coordinated build process before packaging rather than rebuilding during installation.

Minimum installation checks are `bin/forgeflow-server --help`, `bin/forgeflow-worker --help`, `bin/forgeflow --help`, and `bin/forgeflow-sandbox-guard --help`; they do not start execution. Confirm `console/index.html` is present and run the packaged `ops/package-checkpoint.py verify --package /absolute/forgeflow-version` before starting a service.

Native user-owned PostgreSQL can be started with `ops/postgres-local.sh start`; it installs extracted PostgreSQL 16 binaries under the user cache and starts only its own cluster on loopback port 55432. Export the printed DATABASE_URL (unix socket), provide an absolute FORGEFLOW_DATA_ROOT, distinct random owner/worker tokens of at least 24 characters, and an initial owner password of at least 12 characters. Set `FORGEFLOW_CONSOLE_DIR=/absolute/forgeflow-version/console` and keep persistent data outside the install directory. Start `/absolute/forgeflow-version/bin/forgeflow-server`; it migrates before serving and defaults to `127.0.0.1:8787`. Check `FORGEFLOW_API_URL=http://127.0.0.1:8787 /absolute/forgeflow-version/bin/forgeflow health` or `GET /healthz`. Open http://127.0.0.1:8787 and log in using the owner password. Argon2id password hash and revocable eight-hour sessions persist in mode-0600 auth.json. Health success alone does not prove login persistence, restore or Worker/DSH qualification.

`forgeflow health`, `forgeflow projects`, `forgeflow get /projects/<id>`, `forgeflow command /projects --file project.json`, and `forgeflow events <id>` use the same authenticated routes as the console. Supply secrets through environment, not command history or logs. Worker uses `forgeflow-worker --config worker.json`, FORGEFLOW_WORKER_TOKEN, the exact independently qualified profile home (configured explicitly, not silently rewritten), and explicitly selected mode-0600 model secret files. Worker config data_root must equal server data_root in the single-node topology for log/artifact access. Profiles are immutable versioned execution capabilities; unsupported DSH capabilities remain blocked.

Compose from the complete source checkout: copy deploy/env.example to a private environment file, fill absolute persistent/project paths and secrets, create a private data directory owned by your service UID and set FORGEFLOW_UID/FORGEFLOW_GID to match it (both default1000), then `docker compose --env-file private.env -f deploy/compose.yaml up --build -d`. The image build includes the sandbox guard alongside the server, Worker and CLI. The local directory package above is a separate native installation route. PostgreSQL stays private; HTTP host port binds loopback. The nonprivileged Worker runs natively in its configured execution environment; the Compose server cannot execute jobs by itself. No Docker socket or broad home mount is used. Native/Compose share Rust binaries and environment configuration. Remote exposure requires a TLS reverse proxy and protected private access. Bare DSH ACP is never published.

Back up: ensure PostgreSQL client tools are on PATH and export DATABASE_URL and the Owner token through private configuration. Run `ops/backup.py --destination /fresh/backup --data-root /persistent/data --repository /explicit/project`, repeating `--repository` for every managed project. It pauses projects through revision-protected Owner commands, refuses unsettled attempts, performs a PostgreSQL custom dump, copies the data root and listed repositories, and verifies the copies against the quiescent source. Root-level `backups/` is excluded to prevent recursive backups; files named `backups` inside project source remain included. The manifest records exact file hashes, symlink targets, event cursors, project revisions, original data/repository paths, Git refs and `main` SHA. Before/after event, policy, file and ref checks reject concurrent writes without issuing a valid manifest. Projects stay paused for review. Keep the backup directory private: it includes password hashes and authentication state. External DSH installations, private model configuration, executor profiles outside the data root, secrets and release binaries require separately protected escrow and qualification.

Restore: provision a fresh isolated empty PostgreSQL database and choose a nonexistent destination. Put its DATABASE_URL in a private mode-0600 JSON environment file; use `ops/restore.py --backup /backup --destination /fresh/restore --database-env /private/restored-env.json --reset-owner-password`. File inventories, hashes and symlink targets are verified before copying or SQL. Any existing user relations reject the target. PostgreSQL restores in one transaction, saved browser sessions are removed, and the optional reset clears the old password hash for a new password at startup. Preserve failed directories and select another fresh destination rather than overwrite evidence.

For current backups, restore creates `/fresh/restore/restore-relocation.json` with every managed repository's old/new path and exact `main` SHA. Review this file, then run the qualified server binary's offline maintenance entry with DATABASE_URL from private environment: `forgeflow-server --restore-relocation-manifest /fresh/restore/restore-relocation.json --data-root /fresh/restore/data`. This command holds the new data-root lock, validates complete paused-project mapping, Git identities and artifact bytes, changes current authority paths and artifact locators transactionally, emits its receipt and exits before HTTP or dispatch starts. The manifest's `manifest_hash` is SHA-256 of compact UTF-8 JSON excluding that field: fixed top-level order `old_data_root,new_data_root,repositories`; each repository uses `project_id,old_path,new_path,main_sha`. Changing a mapping requires a newly computed hash. Historical attempt envelopes and delivery evidence retain their original identities. Old backup versions without path metadata require an explicitly reviewed mapping; no automatic qualification is inferred.

Initialize distinct NEW Owner and Worker service tokens and a NEW Owner password (all in private environment), set FORGEFLOW_DATA_ROOT to the new `/fresh/restore/data`, and start once with `FORGEFLOW_RESTORE_MODE=1`. This revokes old leases/gateway grants and resets old Worker liveness. Verify login, historical Flow/contracts, exact Git refs, artifact hashes and logs, then register NEW Worker IDs and requalify relocated external executor profiles before any new task. Remove the one-time restore flag for ordinary subsequent starts. Keep projects paused until the review is complete. A recovery rehearsal can temporarily rename the stopped original fixture root, prove that actual history/artifact/log reads and a server restart work without that path, then restore the fixture for evidence preservation. This demonstrates the exercised local recovery scope; new task execution, power-loss recovery and production RTO/RPO require their own actual evidence.

Failures: API exit -> restart, check DB and durable project cursors. Worker lost -> inspect live process fingerprint and preserve held allocation; recovery requires confirmed stop. DSH start failure -> inspect pinned profile, sanitized stderr, private model configuration and Doctor; never substitute mock success. Lease stale -> reject events/results, stop process and preserve evidence. Backup with active attempts -> wait/cancel/confirm stop, rerun; never copy actively written repositories. Upgrade -> retain old binaries/profiles while attempts settle, back up, migrate with one server authority, then validate before resume.

Optional gateway: set FORGEFLOW_GATEWAY_CONFIG to a private JSON file with route_id/model/exact upstream_messages_url/upstream_secret_file/limits/timeout_seconds. Upstream secret is owner-only; a distinct HMAC issuer seed persists privately in data_root/gateway-issuer.secret. Scope-token replay checks current immutable generation/route/model and cannot reset request/inflight counters. Model traffic direct_observed has different enforcement claims and is labelled accordingly.

Server owns a nonblocking data-root OS lock. Before scheduling on restart it reads registered verifier roots, reconciles fingerprinted process groups and writes STOPPED/NEVER_LAUNCHED settlement only after actual proof. Uncertain verifier groups preserve quarantine. FORGEFLOW_RESTORE_MODE=1 additionally revokes restored workers/leases and refuses unsettled attempts. Offline relocation runs before those ordinary startup services; it is a recovery operation with exact mapping and receipts, and its success alone does not qualify a new task or external executor.


### 中止受控容量验证

Owner POST `/projects/{project}/channel-pool/drain` accepts optional `abort_before_end:true` with the current `expected_revision` and a nonblank `reason`. This explicitly aborts qualification and permits early DRAINING; original `starts_at`, `ends_at` and baseline remain immutable. The persisted `qualification_aborted:true` remains through ENDED and cannot be erased to claim the original interval passed. Worker stop acknowledgements still require their original identity and real process-stop evidence before allocations release. `/end` uses the ordinary revision/reason body and requires zero scoped allocations; it never creates stop proof. Omitted/false abort retains the prior elapsed-window contract and serialized request digest.

受控池中历史字段 `launch_grace_ms:2000` 保留以读取原始收据；逐次物理启动延迟作为观测指标记录，不再阻止已合法启动的后续任务结算。活动准入仍检查完整资源向量、有效租约、唯一谱系和真实停止证据；128通道/3600秒、查询P95≤500ms及实际界面事件P95≤2s仍单独验收。提前中止的运行始终保持失败资格。
