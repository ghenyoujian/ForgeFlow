# P0-01 dirty-source declaration model — research only

The required result is a reproducible frozen source candidate without resetting the user's working tree. The existing v2 manifest hashes `git diff --binary HEAD` and status-derived paths; that does not encode the distinct intermediate index when staged and unstaged edits cancel. The present v3 path requires index equal HEAD, rejects untracked business paths, and its public producer is blocked. This research model is a pure in-memory representation, not a filesystem/Git adapter, contract version, or Gate evidence.

Inputs are four caller-supplied mappings keyed by raw POSIX path bytes: HEAD tree, stage-0 index, live tracked worktree, and untracked business files. The caller supplies file/symlink kind, bytes and Git-shaped mode (`100644`, `100755`, `120000`). For working regular files only, `mode=null` records unavailable executable metadata and cannot be silently replaced with index mode; identical bytes and unknown mode yield `INDETERMINATE_MODE`. Symlink bytes are opaque and never followed. A staged deletion followed by an untracked file at the same HEAD path is represented in both the deletion and untracked projection. Renames are exact delete/add observations rather than Git similarity guesses. File-to-directory changes are accepted across different projections but conflicting paths within one candidate are rejected. Binary/non-UTF8 paths are base64; no normalization changes byte identity. Different filesystems may nevertheless be unable to materialize a declared path set.

Each projection item includes byte length, SHA-256 and calculated Git blob ID using the declared repository object format; the returned in-memory blob map supplies content for independent materialization. The commit ID and all inputs are claims; computed blob IDs do not authenticate their association to the claimed commit/index. A caller-provided set lists omitted paths and reasons; exact overlap and ancestor/descendant conflicts with each HEAD, index and working projection are rejected independently, including entries deleted in a later projection. Cross-projection file-to-directory transitions remain allowed. Exclusions must be approved generated data, not business input. An excluded entry's *content* is intentionally not committed; a mistaken exclusion can hide changes and prevents qualification. Each projection has a boolean completeness **claim**; absence is flagged `MISSING_UNCONFIRMED` or `EXTRA_UNCONFIRMED` when the opposite projection's completeness claim is false. Even true claims are not authenticated. Canonical sorted ASCII JSON excludes time and process-specific paths; identical claims/bytes yield the same SHA-256. Any represented content, path, kind, mode, coverage claim, commit claim or exclusion reason changes the canonical bytes; cryptographic collision resistance is an assumption, not a proof of unequal digests.

The prototype rejects unknown entry types, malformed paths, `.git` components, index/untracked overlap, directory/file collision and bounded input excess. It does not handle gitlinks/submodules, unresolved multi-stage index entries, intent-to-add, sparse/skip-worktree/assume-unchanged, linked worktrees, nested repositories, worktree filters, LFS, case/Unicode/NTFS aliasing, xattrs/ACLs, ownership, hardlinks, alternate data streams, sparse files, hostile same-UID races or arbitrary filename materialization. An eventual reader must either represent each feature with explicit semantics and independent validation or return INCONCLUSIVE before omitting it. Full head/index object IDs, mode and blob bytes must be read and verified; independently capture both HEAD→index and index→worktree rather than rely on one combined diff. Git ignored status is not the exclusion authority; tracked files remain in scope even when an ignore rule matches.

Next real path: freeze an approved exclusion policy and schema, implement an isolated read-only collector with bounded byte/path budgets, record full HEAD/index and worktree evidence, preserve changes and untracked bytes in a content-addressed bundle, materialize into a new disposable candidate, and independently compare its full final inventory plus staged/index projection. A controlled trusted-principal execution boundary and an independent verifier must record raw command/status/exit and validate no original modifications; observation alone is non-atomic, and endpoint equality cannot preclude changes and reversions between samples. The current 9p mode limitation requires an explicitly authorized mode source or indeterminate/blocked result; guessing index mode for untracked files is forbidden. Source/principal/lease, environment and product G0 remain unverified.

## Raw HEAD commit and tree association (research only)

`verification/ecp/dirty_source/head_object.py::verify` takes caller-supplied HEAD rows, blob bytes and the exact raw Git commit body. It recomputes each Git blob object ID, reconstructs ordinary blob/symlink trees using byte-path ordering and checks both the commit object ID and its `tree` header. It returns the original commit body and reconstructed tree bodies; it does not read Git, authenticate their source or validate the full commit grammar. Path depth, aggregate path bytes, tree-node count, blob bytes and output trees are bounded; inputs outside these bounds are rejected, not omitted. SHA-1/SHA-256 equality is subject to the relevant collision-resistance assumptions. It does not retrieve parent/history objects, validate source completeness, index or working tree, authorize exclusions, prove atomicity or grant P0-01/G0 qualification.

The [24-method mock red/green receipt](/home/chenyoujian/.cache/forgeflow-g0-continuation-20261116/r39-head-object-research-v2/receipt.json) records three expected v1 limit failures and 24 successful v2 methods; the [single synthetic Git observation](/home/chenyoujian/.cache/forgeflow-g0-continuation-20261116/r39-head-git-run-v1/receipt.json) compares raw commit, seven blobs and three tree bodies with real Git in a private tmpfs. An independent reviewer checked the recorded bytes and object IDs. This SHA-1 synthetic fixture includes nested names, file/directory prefix sorting, a non-UTF-8 filename, executable mode and a symlink; it is one controlled case, not real-source or arbitrary-commit verification.
